# BARSA SHOPI v8.1 — Render Stability Final

## Goal
Harden long mobile renders so transient mux/audio/backend/storage pressure does not destroy a completed AI render.

## Real issues found and corrected

1. **Encoded-chunk write backlog could grow independently of the WebCodecs queue.**
   - Added a second bounded back-pressure layer for OPFS/native mux writes.
   - 4K and >60 FPS use a queue of 2; lighter jobs use 3.
   - Encoder queue is also dynamically bounded.

2. **Native MP4 mux failure could previously lose the render near the end.**
   - The elementary H.264 stream is now treated as the durable recovery copy.
   - A native mux packet/finalize failure disables only Native MP4.
   - The already-rendered H.264 is recovered through FFmpeg remux instead of restarting the AI render.

3. **Native AAC streaming failure could previously abort the finished video render.**
   - A failed native AAC path now cancels the partial MP4 and falls back to FFmpeg AAC/remux using the original source audio.

4. **FFmpeg WASM stayed resident after a fallback/remux.**
   - FFmpeg is now terminated after jobs that use it, releasing the large WASM heap before the next render.

5. **Stabilization and Temporal Reconstruction retained history across jobs.**
   - Both engines are explicitly destroyed after every render so the next video cannot inherit old frame history and retained canvases.

6. **Completed/aborted OPFS sessions accumulated across app launches.**
   - Terminal sessions are pruned on startup because they are not resumable.
   - After Android gallery save, the corresponding render session is removed from OPFS.

7. **Version metadata mismatch.**
   - Android: versionCode 81 / versionName 8.1.0.
   - package.json and package-lock.json: 8.1.0.
   - GitHub debug/release artifact names: v8.1.

## Important runtime behavior
The preferred render path remains:
Native Android ONNX tile inference -> WebGPU/WASM fallback -> WebCodecs H.264 -> Native MP4 when safe.
If Native MP4/AAC fails after video processing, BARSA now preserves the completed elementary video and remuxes it through FFmpeg rather than discarding the render.

## Device note
No software can truthfully guarantee zero crashes without a real long-duration POCO F6 device run. v8.1 specifically removes the main code-level failure modes found in the pipeline and makes recoverable mux/audio failures non-fatal.
